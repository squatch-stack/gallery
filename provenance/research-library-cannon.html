--up and --heading, and the rotation that got them backwards
 
A gallery mesh carries no orientation of its own. cannon-mesh.glb lands
Z-up because RealityKit writes it that way; a Scaniverse export need
not, and an elevation rendered against the wrong up is a picture of the
roof labelled "front".
 
--up takes 'z' (the default), 'auto', or an explicit vector. 'auto'
estimates the ground normal as the thinnest principal axis of the vertex
cloud and always prints what it found, because an estimator that is
silent about its guess is worse than no estimator. --heading rotates
every azimuth together, so an operator can name which way a building
faces; no estimator can invent a canonical front for a photogrammetry
mesh.
 
The rotation was wrong on the first pass and would have shipped
plausible-looking pictures. I built it from up x z with the operands
reversed, so it took the up vector onto MINUS Z: a proper rotation,
determinant +1, orthonormal, and upside down. The test now asserts the
image is +Z rather than merely that the matrix is a rotation, across
seven up vectors including the cannon's real one.
 
On the springhouse this changed nothing, and that is worth recording
because I had already claimed otherwise. I read its first elevation as
a roof seen from above and it was not: the springhouse is a
barrel-vaulted structure built into a hillside, its front IS the arched
facade, and azimuth 0 was pointing at it correctly the whole time. An
eight-azimuth contact sheet settled it. The tool gained two real options
and the mesh needed neither.
 
Twenty new tests, none needing Blender.
